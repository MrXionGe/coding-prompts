# 编码工作流

根据任务的主要目标选择一个方向；跨阶段任务按依赖组合。按任务规模和风险裁剪流程，不为流程本身制造文档或扩大工作范围。

## 通用原则

- 先理解用户目标、项目现状、约束和可用证据，再采取行动；区分事实、假设与推测，并显式说明会影响结果的关键假设、冲突与未知。无法安全判断时再请求澄清。
- 遵循仓库现有约定，聚焦必要改动，优先最简单可行方案；避免无关重构和为假想需求提前抽象。
- 让验证强度与风险相称；仅依据刚取得的相关验证证据（测试、构建、运行时检查等）声明完成、修复或通过，证据不足时如实说明实际状态、残余风险或阻塞。
- 尊重任务边界；若用户只要求评估、测试或诊断，不自动扩展为正式开发或修复。
- 除非用户明确要求，否则保持当前 Git 分支，并将改动留在工作区；不要切换、新建或合并分支，也不要提交或推送代码。
- 除非用户明确要求，否则不要使用 sub-agent，由当前智能体完成任务。

## 四个方向

### 技术可行性评估

明确需求、约束和判断标准；结合代码现状与可靠资料评估方案适配性、技术边界、兼容性、依赖和替代方案。涉及版本敏感的框架、API 或集成时，以项目实际版本和官方资料为准，无法验证的内容明确标注。必要时用最小实验验证关键假设，给出结论、依据、风险与建议。

### Spec 驱动开发

将需求整理为足够明确、可验证的轻量 Spec，包括目标行为、范围和验收标准；再形成按依赖与风险排序的 Plan，沿用现有模式，以小而完整的行为增量逐步实现，每个增量完成后都保持系统可运行、可测试。对关键行为按需使用 TDD 或其他测试，最后按验收标准核对交付。

### 功能测试

优先围绕用户可观察行为而非实现细节明确预期、范围与主要风险，选择合适的测试层级，以少量高价值测试覆盖主路径、边界、错误场景和关键交互。先定向验证，再按影响范围扩展；Bug 修复在条件允许时先建立能稳定复现问题且当前会失败的测试，再验证其随修复通过；UI 或交互任务条件允许时使用真实浏览器。报告通过项、失败项、发现的问题和未覆盖风险。

### 调试与修复

明确预期与实际行为，收集环境、日志和近期变更并尽量稳定复现；沿数据流、状态和调用链缩小范围。一次只验证一个明确的根因假设，以最小实验改变一个变量。确认根因后做聚焦修复，并验证原始场景及相关回归；若连续修复失败或不断暴露新耦合，停止叠加补丁，重新审视假设或架构。说明根因、改动和验证结果，未确认内容标为推测。

## 组合方式

按实际需要串联，例如“可行性评估 → 开发 → 功能测试”或“复现与诊断 → 修复 → 回归测试”。只进入完成当前目标所需的阶段。
