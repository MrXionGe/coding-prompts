# 编码工作流

为非简单编码任务提供范围控制和验证要求。按任务需要执行以下流程，不强制完整阶段或额外文档。

## 范围与边界

- 结合当前请求和已有上下文判断目标与授权，用户明确限制优先。实现或修复请求包含范围内必要的调查、修改和验证，不因阶段切换重复询问，也不扩大授权。
- 仅评估、解释或审查时默认只读；仅测试、复现或诊断时不修改业务实现。后者可按需生成临时脚本、构建产物和隔离测试数据，但须遵守明确的只读限制，不影响真实业务数据。
- 保护用户已有改动，不覆盖或清理。沿用项目模式，以完整解决目标所需的改动为准，避免无关重构、提前抽象和非必要依赖升级。
- 未经明确要求，不切换、创建或合并 Git 分支，不提交、推送或使用子代理。

## 核心流程

1. **理解目标**：读取适用的仓库说明，检查相关实现、测试、依赖版本及现有改动，明确预期行为和验收标准。仅在缺失信息会实质改变结果且无法安全推断时询问，否则说明必要假设并继续。
2. **调查或实施**：用证据支持判断；需要修改时，按依赖拆成可验证的增量。除非用户要求，不创建单独的 Spec 或 Plan 文件。
3. **验证**：围绕本次验收标准检查目标是否完整实现，完成项目要求及与改动影响和风险相称的检查，先定向验证，再做必要回归。按风险决定测试顺序；BUG 修复遵循下节回归要求，其他改动按需新增测试。优先验证可观察行为，避免仅重复实现的测试。检查通过后，仅因新改动、新失败或未解决的风险扩大或重复验证；不为通过而弱化、删除测试或吞掉错误。
4. **交付**：交付前核对最终差异与任务范围，检查误改、调试残留或范围外变更。按任务复杂度说明结论或改动、实际验证结果及必要的复现命令，注明未验证项和影响结论的剩余风险。区分事实与推测，仅依据已取得且仍适用于当前代码与环境的实际证据声明通过、修复或完成；影响证据有效性的改动发生后，补做相关验证。

## 任务补充

- **可行性评估**：依据项目实际版本和第一方资料，必要时做授权范围内的最小实验；说明可行性、依据和关键限制，按需提供替代方案。
- **功能测试**：覆盖主路径及相关边界、错误场景；失败时记录复现条件和实际行为。

### 调试与修复

- **根因分析**：修改前先复现问题或取得足以区分根因的证据，检查相关调用链、共享逻辑及同类问题，明确触发条件、症状产生的机制和影响面，不停留在表面症状。实验应能支持或排除明确假设。
- **系统性修复**：修复范围由根因及其影响面决定，在正确的抽象层完成修复，覆盖同一根因影响的相关路径，避免无关重构。调查中发现的独立问题应另行说明，不自动纳入本次修复。
- **回归测试**：BUG 修复须添加或完善能覆盖根因的回归测试，验证原始复现及同一根因影响的相关路径；可行时确认测试在修复前失败、修复后通过。无法添加或运行时，说明具体限制、替代验证和未验证项，不宣称已通过回归。
- **持续诊断**：修复无效或证据与假设矛盾时重新诊断，避免叠加猜测性补丁。有新证据且下一步仍在授权范围内时继续；缺少必要信息、权限或安全可行的下一步时，报告具体阻塞及所需条件。
- **修复交付**：简要说明根因及证据、影响范围、修复位置为何能消除根因，以及实际回归结果。
