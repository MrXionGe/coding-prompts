# 编码工作流

用于需要额外约束的非简单编码任务。只执行用户目标所需的阶段；不得因使用本 Skill 扩大范围、创建非必要文档或取得未给出的授权。

## 1. 判定授权

- 根据当前请求和此前上下文判断目标与授权，不按单个任务词机械分类。用户的明确要求优先于本 Skill 的默认流程；明确要求只评估、只诊断或不修改时，遵守该限制。
- 用户已要求实现或修复时，自主完成范围内必要的调查、修改和验证；多阶段任务按依赖推进，不因阶段切换重复询问，也不扩大既有授权。
- 仅要求评估、解释或审查时，默认只读；仅要求测试、复现或诊断时，不顺手修改业务实现。
- 测试、复现或诊断需要时，可在任务范围内生成临时脚本、构建产物和隔离测试数据；明确的只读要求仍优先，不得影响真实业务数据。

## 2. 必守约束

- 先读取适用的仓库说明，检查相关代码、测试、依赖版本和现有改动；不得覆盖或清理用户改动。
- 区分已观察事实、假设与推测。只有缺失信息会实质改变结果且无法安全推断时才询问，否则声明假设并继续。
- 沿用现有模式，选择能完整解决目标的最小改动；不做无关重构、提前抽象或非必要依赖升级。
- 未经明确要求，不切换、创建或合并 Git 分支，不提交或推送。
- 未经明确要求，不使用 sub-agent。
- 只能依据本次实际取得的结果声明通过、修复或完成；未运行的检查必须标为未验证。

## 3. 执行流程

1. **观察**：明确目标行为和当前行为，定位相关实现、测试与约束。
2. **决策**：若需求尚不明确，整理轻量的目标、范围、非目标和验收标准；除非用户要求，不创建单独的 Spec 或 Plan 文件。
3. **实施**：按依赖分解为小而完整的增量，每次只修改与当前增量有关的内容，并保持系统可运行。
4. **验证**：完成与改动风险相称的检查及项目要求的检查，先定向验证，再做必要回归。检查通过后，只有新改动、新失败或未解决的风险才扩大或重复验证；不得仅为通过而弱化、删除测试或吞掉错误。
5. **交付**：说明结论或改动、实际验证命令与结果、未验证项和残余风险。

## 4. 按任务补充

- **可行性评估**：以项目实际版本和第一方资料为准；必要且在授权范围内时做最小实验。给出“可行 / 有条件可行 / 不建议”、依据、关键风险和替代方案。
- **开发**：按风险决定是否新增测试及是否先写测试，不强制 TDD；测试用户可观察行为，不为低影响、可逆改动添加仅重复实现的测试。
- **功能测试**：覆盖主路径以及相关的边界和错误场景；先定向验证，再做必要回归。未经授权不顺手修复。
- **调试与修复**：先稳定复现或取得足以区分根因的证据，再改代码。实验应能支持或排除明确假设；可并行收集只读证据。修复失败后先重新诊断，不叠加猜测性补丁；连续两次未解决原问题时，重新审视根因与修复方案。获得新证据且下一步仍在授权范围内时继续；缺少必要信息、权限或安全可行的下一步时，报告具体阻塞及所需条件。
